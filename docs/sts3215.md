# Feetech STS3215 — protocol notes

Verified against two independent sources:

- The official **"ST3215 memory register map-EN.xls" V3.7**
  ([Waveshare](https://files.waveshare.com/upload/2/27/ST3215%20memory%20register%20map-EN.xls)),
  which is the manufacturer's own control table — the authority for register
  addresses, defaults and units.
- [LeRobot's Feetech tables](https://github.com/huggingface/lerobot/blob/main/src/lerobot/motors/feetech/tables.py),
  a well-tested in-production implementation, used to cross-check the value
  encodings.

## Basics

| Property | Value |
|---|---|
| Protocol | Feetech **SMS/STS**, protocol version **0** |
| Model number | 777 |
| Resolution | **4096** steps per revolution |
| Default baud | **1,000,000** (baud table index 0) |
| Default ID | 1 |
| Bus | half duplex, single data line |

⚠️ The older **SCSCL** series is big-endian. The **STS/SMS** series used here is
**little-endian**. Mixing them up produces garbage positions.

## Frame format

```
0xFF 0xFF | ID | LENGTH | INSTRUCTION | PARAM… | CHECKSUM
```

- `LENGTH = number_of_params + 2`
- `CHECKSUM = ~(ID + LENGTH + INSTRUCTION + Σparams) & 0xFF`

| Instruction | Value |
|---|---|
| PING | `0x01` |
| READ | `0x02` |
| WRITE | `0x03` |
| REG_WRITE | `0x04` |
| ACTION | `0x05` |
| RESET | `0x06` |
| SYNC_WRITE | `0x83` |

Because the bus is half duplex, the adapter board echoes what you transmit. The
DoorBot component tolerates this by hunting for the `0xFF 0xFF` header in the
receive stream rather than assuming the reply starts at byte 0.

## Control table (the registers DoorBot uses)

### EEPROM

| Addr | Size | Name |
|---|---|---|
| 5 | 1 | ID |
| 6 | 1 | Baud_Rate |
| 9 | 2 | Min_Position_Limit |
| 11 | 2 | Max_Position_Limit |
| 16 | 2 | Max_Torque_Limit |
| 28 | 2 | Protection_Current |
| 19 | 1 | Unloading_Condition (which faults cut torque) |
| 31 | 2 | Homing_Offset |
| 33 | 1 | Operating_Mode |
| 34 | 1 | Protective_Torque (% output after a fault) |
| 35 | 1 | Protection_Time (×10 ms) |
| 36 | 1 | Overload_Torque (% that counts as overload) |

### SRAM

| Addr | Size | Name |
|---|---|---|
| 40 | 1 | Torque_Enable |
| 41 | 1 | Acceleration |
| 42 | 2 | Goal_Position |
| 44 | 2 | Goal_Time |
| 46 | 2 | Goal_Velocity |
| 48 | 2 | Torque_Limit |
| **55** | 1 | **Lock** |
| 56 | 2 | Present_Position |
| 58 | 2 | Present_Velocity |
| 60 | 2 | Present_Load |
| 62 | 1 | Present_Voltage |
| 63 | 1 | Present_Temperature |
| 65 | 1 | Status |
| 66 | 1 | Moving |
| 69 | 2 | Present_Current |

**Registers 56–63 are contiguous**, so position, velocity, load, voltage and
temperature come back from a **single 8-byte READ**. DoorBot's `update()` does
exactly that instead of five round trips.

## The `Lock` register (55)

This is the **EEPROM write-protect flag**, not a mechanical lock. To change any
EEPROM value:

```
write Lock = 0     # unlock EEPROM
write <register>
write Lock = 1     # re-protect
```

LeRobot's `enable_torque()` writes `Torque_Enable = 1` then `Lock = 1`.

## Sign-magnitude values

Some registers are **sign-magnitude**, not two's complement — the sign lives in
a specific high bit and the rest is the magnitude. From
`STS_SMS_SERIES_ENCODINGS_TABLE`:

| Register | Sign bit |
|---|---|
| Present_Load | 10 |
| Homing_Offset | 11 |
| Goal_Position | 15 |
| Goal_Velocity | 15 |

Decoding:

```c
int decode(uint16_t raw, uint8_t sign_bit) {
  const uint16_t magnitude_mask = (1 << sign_bit) - 1;
  const int magnitude = raw & magnitude_mask;
  return (raw & (1 << sign_bit)) ? -magnitude : magnitude;
}
```

So `Present_Load` reads 0–1023 in either direction, with bit 10 as the sign.
DoorBot's jam detection compares `abs(load)` against a threshold.

## Practical notes for a door lock

- **Torque limit (48)** — cap this. A STS3215 makes ~19–30 kg·cm and will
  happily destroy a thumbturn or strip the mechanism. Start around 700/1000.
- **Acceleration (41)** — a low value makes the turn smooth and quiet.
- **Goal_Velocity (46)** — the STS3215 uses this as a speed cap in position
  mode; ~800 is a sensible starting point.
- **Position limits (9/11)** — set these once calibrated so a bad command can't
  drive the bolt into a hard stop.
- **Homing to a stall** — drive slowly in one direction and watch
  `abs(Present_Load)` until it exceeds a threshold, then stop and read
  `Present_Position`. That end point is the mechanical stop.
## Multi-turn

A euro cylinder usually needs more than one full turn, so DoorBot supports it
directly — no gearing, no external programming tool.

The official table says of registers 9 and 11, verbatim:

> When performing multi-turn absolute position control, this value is set to 0.

So setting **Min_Position_Limit (9) = 0 and Max_Position_Limit (11) = 0** — both
in EEPROM — switches the servo from "one revolution" to multi-turn absolute
positioning. `Goal_Position` then accepts **−30719 … 30719** (±7.5 turns) and
`Present_Position` reports the accumulated multi-turn value.

Two consequences worth knowing:

- **The revolution count is not kept across a power cut.** The manufacturer's
  header note states this outright. After a reset the servo believes it is
  within the first turn, so DoorBot re-homes rather than trusting a stored
  position.
- **Enabling it writes EEPROM.** DoorBot reads each register before writing and
  only writes when the value actually differs, so this happens once rather than
  on every boot — but it is a permanent change to the servo's configuration.

Note this is *not* Operating_Mode 3 ("step servo"), which is relative stepping.
DoorBot stays in mode 0 (position) and just removes the limits.

## Overload protection — why a held latch can slip

This matters for doors with a passive outside handle, where DoorBot has to hold
the latch retracted rather than just pass through a position.

If the load exceeds **Overload_Torque (36)**, default 80%, continuously for
longer than **Protection_Time (35)**, default 200 (= 2 s), the servo drops its
output to **Protective_Torque (34)**, default 20%. A latch spring pushing back
against a 20% output will simply win, and the latch creeps out again.

DoorBot therefore raises Protective_Torque (40% by default, tunable from Home
Assistant) and polls `verify_holding()` throughout a hold, so a slip is reported
instead of silently leaving the door shut.

**Protection_Current (28)** is in units of **6.5 mA**, max 500 → 3250 mA.

## Closed-loop verification

Every DoorBot write parses the servo's ACK status frame rather than firing and
forgetting, so each transaction doubles as a free health check — the error byte
goes straight to the fault sensor. A move is only "arrived" after two
consecutive samples inside the tolerance band, and a jam requires high load
*and* near-zero velocity sustained for ≥350 ms, tested after the arrival check
so that legitimately holding hard on target is never misread as a jam.

## Changing the servo ID

Fresh servos ship as ID 1. If you ever chain more than one:

```
write Lock = 0
write ID = <new>
write Lock = 1
```

DoorBot exposes this as `change_servo_id()` in the ESPHome component.
